## 2026-05-13: v1.0.3 スマホ対応の実装中に学んだ判断

v1.0.3 のスコープ自体は同日のセッション (下記「v1.0.2 ストレージ管理機能とスマホ対応スコープを確定」) で決定済み。ここでは**実装中に踏んだ罠と、その結果採用した判断**を記録する。

### 1. iOS Safari の `position: fixed` はキーボード裏に隠れる

「ここで分割」FAB を画面下部に固定したが、iOS Safari ではソフトキーボード表示時に**レイアウトビューポート基準**で配置されるため、キーボードの裏に隠れた。

**採用した解決策**: `visualViewport API` でキーボード高さを JS で取得し、CSS 変数 `--keyboard-height` に書き込む。CSS 側は `bottom: calc(16px + max(var(--keyboard-height), env(safe-area-inset-bottom)))` で常にキーボード上端のすぐ上に追従する (コミット 662b02b)。

**学び**: モバイル Web の fixed positioning は visual viewport を意識する必要がある。`position: fixed; bottom: 0` は安全に見えて、実は iOS で罠になる。

### 2. bottom sheet を安易に使わない

UX-1 の当初計画では「ヘッダー指標タップ → スマホでは bottom sheet」と決めていたが、実機検証で以下の問題が判明:

1. タップ位置 (右上のアイコン) と表示位置 (画面下) の連続性が崩れ、認知負荷が上がる
2. 同じヘッダー領域にある**ハンバーガーメニューはタップ位置の直下に展開**するのに、ストレージだけ bottom sheet で挙動が一貫しない
3. bottom sheet は画面の半分を占有する重量級 UI で、数行の状態表示には過剰
4. 画面下部要素との重なり/見切れが発生する

**採用した解決策**: PC と同じ「タップ位置直下のドロップダウン」で統一。スマホでは `max-width: calc(100vw - 24px)` で画面端のはみ出しを防ぐ (コミット ed856c5)。

**学び**: bottom sheet が正解になるのは**長いリストからの選択、多段階入力、モーダル的な操作**など。**状態確認の小さな情報**には過剰で、タップ位置 → 表示位置の連続性を守るドロップダウンを優先する。詳細は memory `feedback_tap_to_display_continuity.md`。

### 3. Jinja の `|tojson` は HTML 属性内で使わない

ダッシュボードリネーム実装で `x-data="rowEditor({{ id }}, {{ name|tojson }}, ...)"` と書いたが、`|tojson` の出力ダブルクォートが HTML 属性のクォート境界と衝突し、本番でファイル名が表示されない不具合 (commit 1c3061a → fix 5f6470b)。

**採用した解決策**: 初期データを `<li data-initial-name="{{ name }}">` のように data-* 属性として渡し、Alpine の `init()` で `this.$el.dataset.initialName` から読む。Jinja autoescape が `'` `"` `<` `>` を HTML エンティティに自動エスケープしてくれる。

**学び**: `|tojson` は `<script>` ブロック専用。HTML 属性内では使わない。詳細は memory `feedback_tojson_html_attr.md`。

### 4. iOS の input フォーカスズーム回避は font-size: 16px

スマホで `<select>` や `<input>` をタップしたとき、フォントサイズが 13-15px だと iOS Safari がページを自動ズームイン (Form Zoom)。これは「読みやすくする」という Apple の意図だが、UI が壊れて見える。

**採用した解決策**: モバイルメディアクエリで `.form-select` / `.detail-title-input` / `.segment-text-edit` / `.speaker-popup-input` のフォントサイズを 16px 以上に固定。

**学び**: フォーカス可能要素はモバイルで 16px 以上必須。タッチターゲット (44px) と font-size (16px) はモバイル UI の二大鉄則。

### 5. PC のダブルクリック編集モード入りはスマホで無効化

詳細画面で本文ダブルクリックすると編集モードに入る Notta 互換動線があったが、iOS の拡大ジェスチャー (ダブルタップでズーム) と衝突。ユーザーが意図せず編集モードに入る事故を防ぐため、スマホでは `enterEditMode()` で `window.matchMedia('(max-width: 640px)')` 検出して無効化 (コミット 6da0845)。

**学び**: クロスプラットフォーム UI では「PC で便利な操作」が「モバイルで邪魔」になる組み合わせを意識する。PC 用ショートカット (Shift+Return、ダブルクリック等) はメディアクエリ条件で分岐する。

### 6. SQLite の `DateTime(timezone=True)` は嘘

v1.0.2 で `expires_at` 計算を実装したところ本番で `TypeError: can't subtract offset-naive and offset-aware datetimes`。SQLite は `DateTime(timezone=True)` でも保存時に tzinfo を捨てる。

**採用した解決策**: 読み戻し時に `_ensure_utc_aware()` で naive を UTC として解釈 (コミット 7a4c7de)。

**学び**: v1.0.2 の hotfix だが v1.0.3 のドキュメント更新時に追記。SQLite + SQLAlchemy で datetime を扱うときは aware/naive の境界を意識する。アプリの書き込みは常に UTC で aware にしていれば、読み戻し時の変換は安全。

## 2026-05-13: v1.0.2 ストレージ管理機能とスマホ対応スコープを確定

### 背景

- v1.0 リリース後、A-4 撤回（2026-05-12）により音声がサーバーに永続保管されるようになった
- Railway Hobby Plan のストレージ上限は 5 GB。音声 1 件 50〜120 MB × 月 10〜20 件運用で 1〜2 ヶ月で上限到達の見込み（`ADMIN_OPERATIONS.md` 5.2 節）
- 「ストレージコストが増えるのが嫌」「セキュリティ的にも音声・テキストを長期保管したくない」という市川さん要望
- 同時に、ユーザーがスマホで会議を録音 → 直接アップロードしたいニーズがあり、現状の `.mp3 / .mp4` 限定では iPhone ボイスメモの `.m4a` が弾かれる問題が判明

### 検討した選択肢と決定（v1.0.2 ストレージ管理）

#### 1. 自動削除のスコープ

| 案 | 内容 | 採否 |
|---|---|---|
| α | 音声のみ削除、テキストは永続 | × |
| **β** | **音声 + テキスト + DB レコードの全削除（物理削除）** | **採用** |
| γ | 全削除＋メタデータだけレコードに残す | × |

**β を選んだ理由**: セキュリティ最優先（お客様情報を含む文字起こしを長期保管しない）。エクスポート（TXT/SRT/JSON）で手元保管する動線は既存。

#### 2. 保管期間とそのパラメータ化

- **60 日をデフォルトに**（市川さん判断）
- **環境変数 `DATA_RETENTION_DAYS` で運用中に調整可能**（既存の `MONTHLY_COST_LIMIT_YEN` 等と同様、Variables から変更）
- 60 日は「とりあえずの感覚値」なので、コード変更なしで直せる価値を優先

#### 3. 削除日時を DB カラムにするか

| 案 | 内容 | 採否 |
|---|---|---|
| A | カラム追加なし、`completed_at + DATA_RETENTION_DAYS` を毎回計算（計算ロジック 1 箇所に集約） | **採用** |
| B | `expires_at` カラム追加、完了時に値を保存 | × |

**A を選んだ理由**: 第三者エンジニア視点でレビューし、僕（Claude）が当初 B を推した判断を撤回。理由 3 点:
1. 「延長」「永久保存」など将来機能は現時点で commit されていない（CLAUDE.md「Don't design for hypothetical future requirements」に反する）
2. 「期間変更を過去ジョブに反映する」挙動は、エンドユーザー目線では A の方が自然（「保管期間を伸ばした」と理解できる）
3. 現規模（数十件）でマイグレーション + バックフィルのコストを払う妥当性が薄い

将来「延長」「永久保存」を実装したくなった時点で、Alembic マイグレーションで `expires_at` を追加・バックフィルすれば設計変更は 1 日で終わる。それまでは局所変更で済むよう、期限計算は 1 関数に集約する。

#### 4. 削除予告メール通知

- v1.0.2 では画面のカウントダウン表示のみ（A 案）
- メール通知は将来候補として ROADMAP に記録。利用頻度が低くなる時期や担当者変更時に検討

#### 5. ストレージ使用量バナー

- **70% / 90% の 2 段階で色分け**（黄 / 赤）
- 環境変数 `STORAGE_LIMIT_BYTES`（default 5 GB）/ `STORAGE_WARNING_PERCENT` / `STORAGE_DANGER_PERCENT`
- 70% で気付ければ 1.5 GB の余裕があり、自動削除で「70% を超えるのは異常事態」のシグナルにもなる

#### 6. アップロード時ガード

- **95% で 413 を返す**（C 案）
- 環境変数 `STORAGE_HARD_LIMIT_PERCENT`（default 95）
- DB ファイル成長・一時ファイル展開で予想外に膨らんでも対応できる安全マージン

### 検討した選択肢と決定（スマホ対応）

#### 1. 主目的

- 「**会議終わりにスマホから直接アップロード**」（市川さん要望）
- 副次的に「移動中の閲覧」も対応する（**a+ スコープ**）

#### 2. 対応形式の拡張

| 案 | 追加形式 | 採否 |
|---|---|---|
| 1-a | `.m4a` のみ | × |
| **1-b** | **`.m4a / .wav / .mov` を追加（合計 5 形式）** | **採用** |
| 1-c | AssemblyAI 対応の全主要形式 | × |

**1-b を選んだ理由**:
- iPhone ボイスメモの `.m4a` がスマホ録音の支配的形式（実態シェア 70〜85%）
- iPhone カメラの動画は `.mov` で保存される（「会議を動画として録ってしまった」ケース対応）
- `.wav` は高音質志向のユーザー対応、コストゼロ
- 1-c までやると `.flac / .ogg / .webm` の管理コストが増えるため、主要 5 形式に絞る

#### 3. 編集 UI のスマホ対応

| 案 | 内容 | 採否 |
|---|---|---|
| A | 注意書きだけ、編集可能 | × |
| B | スマホでは編集機能を物理的に隠す | × |
| **C-mobile** | **軽編集 (テキスト訂正・話者リネーム) は OK。Shift+Return とダブルタップは無効化** | **採用** |
| D | スマホでも本格的に編集 (c スコープ) | × |

**C-mobile を選んだ理由**:
- 市川さん談「スマホで編集は少ないが、スキマ時間に内容確認して軽い修正をすることはある」
- B（完全に隠す）はその使い方を塞ぐので厳しすぎる
- 壊れた機能（Shift+Return）と暴発しやすい機能（ダブルタップ→編集モード）だけ無効化すれば実用十分

#### 4. Shift+Return の代案

| 案 | 内容 | 採否 |
|---|---|---|
| A | 長押しで分割メニュー | × |
| **B** | **テキストカードに「✂ ここで分割」ボタン（フォーカス時表示）** | **採用** |
| C | ツールバーに分割ボタン | × |
| D | iOS キーボードアクセサリ | × |

**B を選んだ理由**:
- ユーザー視点: 隠れた機能（長押し）は発見されない
- アートディレクター視点: 視覚的に「このカードの操作」と明確
- カーソル位置で分割するので Shift+Return と完全に同じ動作
- PC でも併存させると Shift+Return を知らないユーザーへの発見性も向上

#### 5. PC のダブルクリックでの編集モード入り

- **PC では残す**（Notta 互換、慣れているユーザーが多い）
- スマホでは無効化（iOS の拡大ジェスチャーと衝突）

### 理由（共通）

- 配布対象は社内 5〜8 人で、UX 摩擦の少なさとセキュリティのバランスを取る
- 環境変数化はすべて「運用中に再デプロイなしで調整できる」価値を重視
- 「将来 X するかも」での過剰設計は避ける（YAGNI、CLAUDE.md の方針）
- UI/UX のビジュアル詳細は**アートディレクター + ユーザー視点の専用レビューセッション**で別途決定（実装着手前に詰める）

### 保留した課題（将来タスク）

- 削除予告メール通知（Gmail SMTP / SendGrid 等の送信基盤選定）
- 管理者向け定期レポート（使用量・コスト・失敗率の通知）
- キーワード検索（文字起こし全文・タイトル・話者名）
- PWA + Web Share Target（iPhone ボイスメモの共有シートから直接アップロード）
- 個別「テキストのみ削除」エンドポイント（API レベルでは既に拡張容易な構造）

### 実装場所（予定）

- `backend/transcribe/retention.py`（新規）: 自動削除タスク、期限判定
- `backend/transcribe/storage_usage.py`（新規）: 使用量計算
- `backend/transcribe/constants.py`: `ALLOWED_EXTENSIONS` 拡張
- `backend/config.py`: 各環境変数の追加
- `backend/main.py`: lifespan に自動削除タスク追加
- `backend/templates/index.html`: ストレージバナー
- `backend/templates/_transcript_row.html` / `transcript_detail.html`: カウントダウン表示・スマホ対応 CSS
- `backend/static/css/style.css`: レスポンシブ対応の `@media` クエリ追加
- `docs/ROADMAP.md`: v1.0.2 / v1.x スマホ対応セクション（追加済み）

## 2026-05-12: A-4「処理後音声即削除」ポリシーを撤回し、音声をサーバーに保管する

### 背景
- v1.0 リリース後、社内配布開始のタイミングでユーザーから「アップロードした音声を聞き直したい」「『あぁ、あのときの会議か』と思い出すためにダッシュボードから再生したい」という要望
- 当初の A-4 ポリシー（DESIGN.md 参照）では、AssemblyAI への送信が終わり次第サーバー側の音声ファイルを即削除していた
- v1.1 で予定していた「クライアント側で音声ファイルを選んで同期再生」方式は、毎回ファイル選択ダイアログが必要で「思い出すための再生」体験としては摩擦が大きすぎる

### 検討した選択肢

| 案 | 内容 | 機密性 | UX |
|---|---|---|---|
| A | サーバー側に音声を永続保管 | サーバーに残る | シームレス |
| B | クライアント側でファイル選択（v1.1 計画） | サーバーに残らない | 毎回ファイル選択が必要 |
| C | ハイブリッド (File System Access API でブラウザに記憶) | サーバーに残らない | Chrome/Edge 限定、デバイス間移行不可 |

### 決定: **案 A（サーバーに保管 + 手動削除）**

具体的には:
- AssemblyAI 完了後、音声ファイルを `/data/audio/{transcript_id}.{ext}` に移動して永続保管
- 詳細画面とダッシュボードの両方から再生可能 (HTML5 `<audio>` 要素 + 認証付き配信エンドポイント)
- ユーザーは詳細画面の「音声を削除」ボタンで手動削除可能（文字起こしテキストは残る）
- 文字起こし全体削除時は音声も一緒に削除

### 理由
- 配布対象は社内 5〜8 人で「お客様情報の取り扱いは社内ルールに従う」前提が共有できる規模
- 「思い出すための再生」ニーズは UX 摩擦の少なさが本質
- 永続ボリュームのストレージコストは数十 GB レベルでは問題にならない
- v1.1 の同期再生（ハイライト・自動スクロール）はこの上に乗せられる

### 保留した課題（将来タスク）
- **自動削除**: 30 日後・60 日後など期限を切って自動削除する仕組み。現状は手動削除のみ
- **保管時の暗号化**: Railway ボリュームは透過暗号化ではないので、機密性をさらに高めたい場合は要対応
- **バックアップ**: 永続音声をバックアップ対象に含めるか要検討

### 実装場所
- `backend/transcribe/storage.py`: `move_to_storage` / `find_stored_audio` / `delete_stored_audio`
- `backend/transcribe/tasks.py`: AssemblyAI 完了後に永続側へ move
- `backend/transcribe/routes.py`: `GET /api/transcripts/{id}/audio` (配信) と `DELETE /api/transcripts/{id}/audio` (手動削除)
- `backend/templates/_transcript_row.html` / `transcript_detail.html`: 再生ボタンと `<audio>` 要素
- Railway 環境変数: `AUDIO_STORAGE_DIR=/data/audio`

## 2026-05-12: 同じ話者名を別話者に付けることは原則禁止

### 背景
- Notta 方式の「すべての○○ に適用」を実装した結果、技術上は別の `speaker_label`（例: 話者A と 話者D）に同じ表示名（例: あつし）を付けることが可能になった
- しかし運用上、議事録を読む人にとって「同じ名前 = 同じ人」という直感が崩れる
- 同名重複が許されると、後から「すべての『あつし』に適用」したときに意図せず別人のセグメントも巻き込まれる

### 決定: **同じ表示名を異なる `speaker_label` 間で共有することは禁止**

具体的には：
- `PATCH /api/segments/{id}` の `display_name` 更新で、別の `speaker_label` に同じ表示名が既に付いていたら **HTTP 400** で拒否
- `POST /api/transcripts/{id}/segments/rename-by-name` 同様
- エラーメッセージで「例: あつしA、あつしB」とユーザー側での工夫を提案

### 理由
- 「同じ名前 = 同じ人」のメンタルモデルを保つ
- 一括変更の意図しない巻き込みを未然に防ぐ
- Notta も同様の運用（ユーザーがサフィックスで区別する）

### 例外: 候補リストから選択した場合は許可する
ポップアップの候補リストから既存名をクリックして選んだ場合は「ユーザーが
明示的に既存の話者にマージしたい」操作と解釈し、重複チェックをスキップする。
ユーザーが直接タイプした場合のみ重複チェックが走る。

実装: フロントの editor 状態に `fromCandidate` フラグを持ち、候補クリック時に
true、タイプ時に false にする。リクエストボディに `force` として送り、
バックエンドはそれが true なら `_check_speaker_name_collision` を呼ばない。

### トレードオフ（受容したもの）
- 「同じ名前で良い」ケースは候補選択経由でしか入り口がなくなる（タイプでは封じる）
- 既存の「一括 (すべて)」操作でも、タイプした名前で同名衝突したら拒否される

### 実装場所
- `backend/transcribe/routes.py::_check_speaker_name_collision`
- `backend/templates/transcript_detail.html` の editor.fromCandidate と
  candidates クリック / input @input ハンドラ
- フロントは 400 レスポンスの `detail.message` を alert() でそのまま表示

## 2026-05-12: v1.1 で「音声同期再生」を追加することに決定（クライアント側再生方式）

### 背景
- v1.0 リリース直前、ユーザーから「Notta のように音声を聞きながら、該当セグメントが自動でハイライトされる機能が欲しい」というリクエスト
- 動機: 会議録音の文字起こし結果を見て編集する際、音声を注意深く聞きながら、誤認識の修正・補足・話者の特定を行いたい
- Notta が標準で持っている機能で、ユーザー業務上の価値が高い

### 検討した選択肢

| 案 | 内容 | 追加コスト | 機密性 | 操作性 |
|---|---|---|---|---|
| A | サーバー側に音声を保持し、ストリーム配信 | ストレージ月額 ↑ | ↓（クラウド保管） | URL 開けばすぐ聞ける |
| B | クライアント側でローカル音声ファイルを開いて再生（サーバーには送らない） | ¥0 | ◎（手元のみ） | 開くたびに音声選択が必要 |
| C | 機能追加せず（v1.0 のまま） | ¥0 | 現状維持 | 同期再生不可 |

### 議論の経緯
1. 最初は A（サーバー保持）案を提示
2. ただし、A-4「AssemblyAI 送信後は音声を即削除」（DESIGN.md / SECURITY.md）の方針と衝突
3. ユーザーから「現在の仕様を変えずに実現できないか？」と提案
4. B（クライアント側再生）であれば、サーバー側を一切変えずに同期再生が実現可能と判明

### 決定: **B（クライアント側再生方式）**

### 理由
- A-4 ポリシー（処理後音声即削除）を維持できる ← 機密性の根幹
- 追加ストレージコスト ¥0
- 音声は一切サーバーに送らない（`URL.createObjectURL()` でブラウザ内のみ）
- DB スキーマ変更なし（`segment.start_seconds` を流用）
- フロントだけの実装で完結 → 開発リスクが小さい

### トレードオフ（受容したもの）
- ユーザーは元の音声ファイルを自分の Mac／OneDrive 等に保持する必要がある
- 過去案件を再聞きしたい場合、元音声を破棄していると不可
  - ただし**文字起こしテキストは引き続き閲覧・編集・エクスポート可能**なので、致命的な制約ではない

### リリース方針
- v1.0 はこの機能を含めずに先行リリース・社内配布
- v1.1 で本機能を追加（タグ: `v1.1-audio-sync`）
- 配布して使ってみないと「保持期間」や「UI 詳細」の妥当性が掴みにくいため、運用ベースで決める

## 2026-05-11〜12: pyannote の MPS / CPU 迷走

### 経緯（時系列）
1. **当初**: pyannote を Apple Silicon GPU (MPS) で実行
2. **問題1**: 44分音声で進捗バーが 1/4 未満で停止、残り「1分」のまま固まる
3. **対応1**: pyannote を CPU 実行に切り替え → 動くが遅い（44分音声に 50分）
4. **対応2**: MPS に戻して `PYTORCH_MPS_HIGH_WATERMARK_RATIO=0.5` でメモリ上限を制御
5. **問題2**: 2時間音声で 16GB Mac がメモリ 15GB 超でクラッシュ・再起動
6. **教訓**: 16GB Mac で 2時間音声を pyannote 単体で安定処理するのは事実上困難

- ローカル ML の安定運用は、想定される全 Mac スペックでの検証が必要で、検証コストが大きい
- 「動く」と「業務で使える」の間に大きな溝があった
- この経験が、AssemblyAI 採用と Web アプリ化への方針転換の決め手となった

## 2026-05-12: 完全非同期設計（スリープ防止しない）

### 当初の提案
- 処理中は Mac のスリープを防ぐ（IOPMAssertion API）
- + ジョブ復帰機能（電源切れ対策）

### 第三者視点での再評価
- スリープ防止は OS の電源管理機能と戦う設計
- バッテリー消費・ユーザー混乱・クラッシュ時のアサーション漏れリスク
- 「2つの実行パス（正常・復帰）」を抱えると、復帰パスのバグが見つかりにくい
- そもそも「サーバー処理待ち」を同期的に扱うのが歪み

### 決定
**完全非同期アーキテクチャ**を中核に据える：
- スリープ防止は実装しない
- ジョブ ID を保存し、いつでも復帰可能にする
- スリープ・クラッシュ・電源切れ・アプリ閉じ全てを「同じ復帰パス」で処理

### 理由
- OS と戦わない設計が長期的に安定
- コード経路が1つに統合される（バグが減る）
- ユーザーの自由度が上がる（処理中に Mac を閉じても OK）
- 将来「フリー＆フォーゲット」拡張が容易
- Notta 的なメンタルモデルに合致
