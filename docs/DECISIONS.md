## 2026-05-12: 同じ話者名を別話者に付けることは原則禁止

### 背景
- Notta 方式の「すべての○○ に適用」を実装した結果、技術上は別の `speaker_label`（例: 話者A と 話者D）に同じ表示名（例: あつし）を付けることが可能になった
- しかし運用上、議事録を読む人にとって「同じ名前 = 同じ人」という直感が崩れる
- 同名重複が許されると、後から「すべての『あつし』に適用」したときに意図せず別人のセグメントも巻き込まれる

### 決定: **同じ表示名を異なる `speaker_label` 間で共有することは禁止**

具体的には：
- `PATCH /api/segments/{id}` の `display_name` 更新で、別の `speaker_label` に同じ表示名が既に付いていたら **HTTP 400** で拒否
- `POST /api/transcripts/{id}/segments/rename-by-name` 同様
- エラーメッセージで「例: あつしA、あつしB」とユーザー側での工夫を提案

### 理由
- 「同じ名前 = 同じ人」のメンタルモデルを保つ
- 一括変更の意図しない巻き込みを未然に防ぐ
- Notta も同様の運用（ユーザーがサフィックスで区別する）

### トレードオフ（受容したもの）
- 「同じ名前で良い」というケースは封じられる（→ 必要なら将来 v1.x で override オプションを追加）
- 既存の「一括 (すべて)」操作でも同名衝突したら拒否される

### 実装場所
- `backend/transcribe/routes.py::_check_speaker_name_collision`
- フロントは 400 レスポンスの `detail.message` を alert() でそのまま表示

## 2026-05-12: v1.1 で「音声同期再生」を追加することに決定（クライアント側再生方式）

### 背景
- v1.0 リリース直前、ユーザーから「Notta のように音声を聞きながら、該当セグメントが自動でハイライトされる機能が欲しい」というリクエスト
- 動機: 会議録音の文字起こし結果を見て編集する際、音声を注意深く聞きながら、誤認識の修正・補足・話者の特定を行いたい
- Notta が標準で持っている機能で、ユーザー業務上の価値が高い

### 検討した選択肢

| 案 | 内容 | 追加コスト | 機密性 | 操作性 |
|---|---|---|---|---|
| A | サーバー側に音声を保持し、ストリーム配信 | ストレージ月額 ↑ | ↓（クラウド保管） | URL 開けばすぐ聞ける |
| B | クライアント側でローカル音声ファイルを開いて再生（サーバーには送らない） | ¥0 | ◎（手元のみ） | 開くたびに音声選択が必要 |
| C | 機能追加せず（v1.0 のまま） | ¥0 | 現状維持 | 同期再生不可 |

### 議論の経緯
1. 最初は A（サーバー保持）案を提示
2. ただし、A-4「AssemblyAI 送信後は音声を即削除」（DESIGN.md / SECURITY.md）の方針と衝突
3. ユーザーから「現在の仕様を変えずに実現できないか？」と提案
4. B（クライアント側再生）であれば、サーバー側を一切変えずに同期再生が実現可能と判明

### 決定: **B（クライアント側再生方式）**

### 理由
- A-4 ポリシー（処理後音声即削除）を維持できる ← 機密性の根幹
- 追加ストレージコスト ¥0
- 音声は一切サーバーに送らない（`URL.createObjectURL()` でブラウザ内のみ）
- DB スキーマ変更なし（`segment.start_seconds` を流用）
- フロントだけの実装で完結 → 開発リスクが小さい

### トレードオフ（受容したもの）
- ユーザーは元の音声ファイルを自分の Mac／OneDrive 等に保持する必要がある
- 過去案件を再聞きしたい場合、元音声を破棄していると不可
  - ただし**文字起こしテキストは引き続き閲覧・編集・エクスポート可能**なので、致命的な制約ではない
- 詳細画面を開くたびに音声ファイルを選択する手間（毎セッションで 1 回）

### リリース方針
- v1.0 はこの機能を含めずに先行リリース・社内配布
- v1.1 で本機能を追加（タグ: `v1.1-audio-sync`）
- 配布して使ってみないと「保持期間」や「UI 詳細」の妥当性が掴みにくいため、運用ベースで決める

### 関連ドキュメント
- 実装計画: `docs/ROADMAP.md` フェーズ 9 (v1.1)
- 機密性ポリシー: `docs/SECURITY.md`（音声サーバー保持しない方針は維持）
- 設計方針 A-4: `docs/DESIGN.md`（処理後音声即削除）

## 2026-05-12: Mac アプリではなく Web アプリで作ることに決定

### 背景
- Mac アプリ版（v0.1）を社内配布する直前の検証段階
- 配布前にメモリ問題・MPS問題などが発覚（後述）
- AssemblyAI 採用を決定した時点で「ローカル処理のメリット」がほぼ消失
- さらに、ユーザーの業務スタイル（直行直帰・コワーキング・ホテル等での作業が多い）が判明

### 検討した選択肢
| 案 | 内容 |
|---|---|
| A | Macアプリ現状延長 + 手動配布 |
| B | Macアプリ + Sparkle 自動更新 |
| C | Web アプリへ全面書き換え |

### 議論の経緯
1. 最初は Web アプリを推奨
2. サーバー運用負荷・単一障害点・大容量ファイル UX・認証システムの必要性を考慮し、B（Mac＋Sparkle）に推奨を訂正
3. しかし、ユーザーの「外出先で作業したい」「アップロードして放置したい」という業務実態が判明
4. これは構造的に Mac アプリでは解決不可能と判断し、C（Web アプリ）を最終推奨

### 決定: **C（Web アプリ）**

### 理由
- 「場所に縛られない」業務スタイルへの本質的フィット
- アップデート配布の悩みが解消
- 「ファイルをアップしておけば勝手に処理しておいてくれる」体験（Notta 的）の本質的な再現
- 5〜8人の小規模社内利用は Web の典型的ユースケース
- Notta の年20万を Web アプリ年1〜3万に抑制できる見込み

### トレードオフ（受容したもの）
- サーバー運用（マネージドサービス活用で軽減）
- 単一障害点リスク
- 認証システムの追加実装
- 初期実装工数の増加（数日 → 数週間規模）

## 2026-05-12: AssemblyAI を採用

### 背景
- pyannote（ローカル話者分離）が 2時間音声で 16GB Mac を OOM クラッシュさせる
- CPU 実行は安定するが 44分音声に 50分かかり、業務利用に耐えない
- 配布先 Mac のメモリ構成が不明、どの Mac でも安定動作させる保証が困難
- ユーザーが Google Drive を業務で使っているため、クラウドサービス利用は心理的・運用的に許容範囲

### 検討した選択肢
| サービス | 強み | 2時間あたり概算 |
|---|---|---|
| AssemblyAI | 日本語＋話者分離の精度バランス、API がシンプル | 約 110円 |
| Deepgram (Nova-3) | 最速、API シンプル | 約 130円 |
| OpenAI Whisper API | 安い | 話者分離なし → 不採用 |
| Google Cloud Speech-to-Text | Google 連携自然 | 約 290円、やや高い |

### 決定: **AssemblyAI**

### 理由
- 日本語の話者分離精度が安定している（実績）
- 料金体系がアカウント数非依存（処理時間ベース）→ Notta 比 90% 削減見込み
- 5〜8人の小規模利用でも 16GB Mac OOM 問題から完全解放
- API がシンプルで実装負担が小さい
- SOC2 / GDPR 準拠、学習データ非利用契約あり

### コスト試算
- 月10〜32時間の処理 → 年 5,000〜23,000円（最悪ケース）
- Notta 5〜8 アカウント年 15〜20万円との比較で 90% 削減

## 2026-05-11〜12: pyannote の MPS / CPU 迷走

### 経緯（時系列）
1. **当初**: pyannote を Apple Silicon GPU (MPS) で実行
2. **問題1**: 44分音声で進捗バーが 1/4 未満で停止、残り「1分」のまま固まる
3. **対応1**: pyannote を CPU 実行に切り替え → 動くが遅い（44分音声に 50分）
4. **対応2**: MPS に戻して `PYTORCH_MPS_HIGH_WATERMARK_RATIO=0.5` でメモリ上限を制御
5. **問題2**: 2時間音声で 16GB Mac がメモリ 15GB 超でクラッシュ・再起動
6. **教訓**: 16GB Mac で 2時間音声を pyannote 単体で安定処理するのは事実上困難

### 学び
- ローカル ML の安定運用は、想定される全 Mac スペックでの検証が必要で、検証コストが大きい
- 「動く」と「業務で使える」の間に大きな溝があった
- この経験が、AssemblyAI 採用と Web アプリ化への方針転換の決め手となった

### 未コミット変更
- 2026-05-12 時点で `transcribe_core.py` に MPS 復帰の試行コードが未コミット状態で残っている
- Web アプリ化の流れで pyannote 自体を削除するため、この変更は採用しない予定

## 2026-05-12: 完全非同期設計（スリープ防止しない）

### 当初の提案
- 処理中は Mac のスリープを防ぐ（IOPMAssertion API）
- + ジョブ復帰機能（電源切れ対策）

### 第三者視点での再評価
- スリープ防止は OS の電源管理機能と戦う設計
- バッテリー消費・ユーザー混乱・クラッシュ時のアサーション漏れリスク
- 「2つの実行パス（正常・復帰）」を抱えると、復帰パスのバグが見つかりにくい
- そもそも「サーバー処理待ち」を同期的に扱うのが歪み

### 決定
**完全非同期アーキテクチャ**を中核に据える：
- スリープ防止は実装しない
- ジョブ ID を保存し、いつでも復帰可能にする
- スリープ・クラッシュ・電源切れ・アプリ閉じ全てを「同じ復帰パス」で処理

### 理由
- OS と戦わない設計が長期的に安定
- コード経路が1つに統合される（バグが減る）
- ユーザーの自由度が上がる（処理中に Mac を閉じても OK）
- 将来「フリー＆フォーゲット」拡張が容易
- Notta 的なメンタルモデルに合致

## 2026-05-12: ステージ B-1 完了（技術スタック確定）

### 確定したスタック
- バックエンド: **FastAPI**（Python 3.12）
- フロントエンド: **HTMX + Alpine.js**
- データベース: **SQLite**
- ホスティング: **Railway**
- 認証: **Google OAuth（authlib）**

### 判断の補助条件
- メンテナンスは **Claude Code またはエンジニア** が担当
- 非エンジニア（ユーザー）がコードを直接読むことは想定しない
- 月額数千円程度のコストは許容範囲

### 検討した代替案と却下理由
- **Flask**: シンプルだが、Claude Code との相性は FastAPI の方が良い（型ヒント・OpenAPI 自動生成）
- **Supabase**: 認証・DB の統合は魅力的だが、ベンダーロックインのデメリットが上回る
- **Render（定額制ホスティング）**: 予算予測しやすいが、Railway の方が DX が良く、コストも許容範囲
- **React/Vue**: 我々の規模では SPA は過剰。HTMX + Alpine で十分

### コスト予測
- 30時間/月利用想定で月額 **¥3,165**（年間 ¥37,980）
- Notta 5〜8アカウント比で **70〜81% 削減**

## 2026-05-12: ドキュメント駆動の開発方針

### 背景
- ユーザーが「不具合の改修を重ねるうちにプログラムがぐちゃぐちゃになって、頓挫することが心配」と表明
- Claude のセッションは記憶が引き継がれない（ファイルとして残さないと消える）

### 決定
- 設計・判断・進捗をすべて `.md` ファイルで残す
- `CLAUDE.md` をルートに置き、新セッションで自動読み込み
- `docs/` 配下に各種ドキュメント
- Git タグでチェックポイント運用

### 効果
- セッション切れ後も状況把握が即できる
- 半年後の「なぜこうしたっけ」を解消
- 過去の判断を裏付けとして参照できる
- 頓挫リスクの大幅低減
