## 2026-05-12: Mac アプリではなく Web アプリで作ることに決定

### 背景
- Mac アプリ版（v0.1）を社内配布する直前の検証段階
- 配布前にメモリ問題・MPS問題などが発覚（後述）
- AssemblyAI 採用を決定した時点で「ローカル処理のメリット」がほぼ消失
- さらに、ユーザーの業務スタイル（直行直帰・コワーキング・ホテル等での作業が多い）が判明

### 検討した選択肢
| 案 | 内容 |
|---|---|
| A | Macアプリ現状延長 + 手動配布 |
| B | Macアプリ + Sparkle 自動更新 |
| C | Web アプリへ全面書き換え |

### 議論の経緯
1. 最初は Web アプリを推奨
2. サーバー運用負荷・単一障害点・大容量ファイル UX・認証システムの必要性を考慮し、B（Mac＋Sparkle）に推奨を訂正
3. しかし、ユーザーの「外出先で作業したい」「アップロードして放置したい」という業務実態が判明
4. これは構造的に Mac アプリでは解決不可能と判断し、C（Web アプリ）を最終推奨

### 決定: **C（Web アプリ）**

### 理由
- 「場所に縛られない」業務スタイルへの本質的フィット
- アップデート配布の悩みが解消
- 「ファイルをアップしておけば勝手に処理しておいてくれる」体験（Notta 的）の本質的な再現
- 5〜8人の小規模社内利用は Web の典型的ユースケース
- Notta の年20万を Web アプリ年1〜3万に抑制できる見込み

### トレードオフ（受容したもの）
- サーバー運用（マネージドサービス活用で軽減）
- 単一障害点リスク
- 認証システムの追加実装
- 初期実装工数の増加（数日 → 数週間規模）

## 2026-05-12: AssemblyAI を採用

### 背景
- pyannote（ローカル話者分離）が 2時間音声で 16GB Mac を OOM クラッシュさせる
- CPU 実行は安定するが 44分音声に 50分かかり、業務利用に耐えない
- 配布先 Mac のメモリ構成が不明、どの Mac でも安定動作させる保証が困難
- ユーザーが Google Drive を業務で使っているため、クラウドサービス利用は心理的・運用的に許容範囲

### 検討した選択肢
| サービス | 強み | 2時間あたり概算 |
|---|---|---|
| AssemblyAI | 日本語＋話者分離の精度バランス、API がシンプル | 約 110円 |
| Deepgram (Nova-3) | 最速、API シンプル | 約 130円 |
| OpenAI Whisper API | 安い | 話者分離なし → 不採用 |
| Google Cloud Speech-to-Text | Google 連携自然 | 約 290円、やや高い |

### 決定: **AssemblyAI**

### 理由
- 日本語の話者分離精度が安定している（実績）
- 料金体系がアカウント数非依存（処理時間ベース）→ Notta 比 90% 削減見込み
- 5〜8人の小規模利用でも 16GB Mac OOM 問題から完全解放
- API がシンプルで実装負担が小さい
- SOC2 / GDPR 準拠、学習データ非利用契約あり

### コスト試算
- 月10〜32時間の処理 → 年 5,000〜23,000円（最悪ケース）
- Notta 5〜8 アカウント年 15〜20万円との比較で 90% 削減

## 2026-05-11〜12: pyannote の MPS / CPU 迷走

### 経緯（時系列）
1. **当初**: pyannote を Apple Silicon GPU (MPS) で実行
2. **問題1**: 44分音声で進捗バーが 1/4 未満で停止、残り「1分」のまま固まる
3. **対応1**: pyannote を CPU 実行に切り替え → 動くが遅い（44分音声に 50分）
4. **対応2**: MPS に戻して `PYTORCH_MPS_HIGH_WATERMARK_RATIO=0.5` でメモリ上限を制御
5. **問題2**: 2時間音声で 16GB Mac がメモリ 15GB 超でクラッシュ・再起動
6. **教訓**: 16GB Mac で 2時間音声を pyannote 単体で安定処理するのは事実上困難

### 学び
- ローカル ML の安定運用は、想定される全 Mac スペックでの検証が必要で、検証コストが大きい
- 「動く」と「業務で使える」の間に大きな溝があった
- この経験が、AssemblyAI 採用と Web アプリ化への方針転換の決め手となった

### 未コミット変更
- 2026-05-12 時点で `transcribe_core.py` に MPS 復帰の試行コードが未コミット状態で残っている
- Web アプリ化の流れで pyannote 自体を削除するため、この変更は採用しない予定

## 2026-05-12: 既存試作（`app_web.py` / `frontend/`）を再利用しない

### 背景
- リポジトリには Flask + PyWebView の試作物（`app_web.py` と `frontend/`）が残っている
- 名前から「Web アプリ」に再利用できそうに見える
- 過去のセッションで Tkinter 版（`app.py`）に方針を一本化し、これらは使われなくなっていた

### 判断
**再利用しない**

### 理由
- 設計思想が今回の Web アプリ（クラウドホスト・SSO・AssemblyAI）と大きく異なる
- PyWebView 経由のデスクトップウィンドウ前提で、純粋な Web サービスではない
- 中途半端に再利用すると、新設計を歪ませてしまう
- ゼロから設計する方が結果的に綺麗

## 2026-05-12: 完全非同期設計（スリープ防止しない）

### 当初の提案
- 処理中は Mac のスリープを防ぐ（IOPMAssertion API）
- + ジョブ復帰機能（電源切れ対策）

### 第三者視点での再評価
- スリープ防止は OS の電源管理機能と戦う設計
- バッテリー消費・ユーザー混乱・クラッシュ時のアサーション漏れリスク
- 「2つの実行パス（正常・復帰）」を抱えると、復帰パスのバグが見つかりにくい
- そもそも「サーバー処理待ち」を同期的に扱うのが歪み

### 決定
**完全非同期アーキテクチャ**を中核に据える：
- スリープ防止は実装しない
- ジョブ ID を保存し、いつでも復帰可能にする
- スリープ・クラッシュ・電源切れ・アプリ閉じ全てを「同じ復帰パス」で処理

### 理由
- OS と戦わない設計が長期的に安定
- コード経路が1つに統合される（バグが減る）
- ユーザーの自由度が上がる（処理中に Mac を閉じても OK）
- 将来「フリー＆フォーゲット」拡張が容易
- Notta 的なメンタルモデルに合致

## 2026-05-12: 話者編集 UX を Notta 風に改修（F-1）

### 背景
- 既存実装でも話者の merge は可能だが、UX が分かりづらい
- ユーザーは Notta の「話者名クリック → ドロップダウン → 既存話者選択 → 全適用」のフローに馴染んでいる

### 決定
- ドロップダウン式の話者編集 UI
- 候補は全過去ファイルから集めた話者名（最近使った順）
- 名前の1文字目をカラー円アイコンで表示
- 「この話者にのみ適用」「すべての XXX に適用」の2択メニュー
- 「未設定話者1」「未設定話者2」表記に統一

### 既存実装からの活用
- データ構造（`Segment.display_name`, `_speaker_names`）はそのまま活用
- UI 部分のみ刷新

## 2026-05-12: ドキュメント駆動の開発方針

### 背景
- ユーザーが「不具合の改修を重ねるうちにプログラムがぐちゃぐちゃになって、頓挫することが心配」と表明
- Claude のセッションは記憶が引き継がれない（ファイルとして残さないと消える）

### 決定
- 設計・判断・進捗をすべて `.md` ファイルで残す
- `CLAUDE.md` をルートに置き、新セッションで自動読み込み
- `docs/` 配下に各種ドキュメント
- Git タグでチェックポイント運用

### 効果
- セッション切れ後も状況把握が即できる
- 半年後の「なぜこうしたっけ」を解消
- 過去の判断を裏付けとして参照できる
- 頓挫リスクの大幅低減
