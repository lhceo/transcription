### フェーズ 9 (v1.1): 音声同期再生（Notta 互換の聞きながら編集）

**目的**: ユーザーが音声を注意深く聞きながら、対応するセグメントを目で追い、編集・補足できる体験を提供する（Notta が標準で持つ機能）。

**ユーザーストーリー**: 「会議録音の文字起こし結果を見ながら、その場面の音声を聞き直し、誤認識の修正・補足・話者の特定をしたい。再生中は現在の発言箇所が自動でハイライト・スクロールされ、カードをクリックすればその時刻にジャンプする。」

#### 前提（重要）

当初は「サーバー側に音声を保持しない / 毎回ローカルファイルを選択」方式を計画していたが、**2026-05-12 に A-4 ポリシー（処理後音声即削除）を撤回**し、文字起こし完了後の音声を `/data/audio/{transcript_id}.{ext}` に永続保管する方針に変更（DECISIONS.md 2026-05-12 参照）。

**そのため、本フェーズの実装スコープは「既に動いている音声再生 UI に、同期ハイライト・自動スクロール・クリックシークを追加するフロント開発のみ」となる**。サーバー側の追加実装は不要。

#### 既に実装済み（フェーズ 9 着手前の現状）

- `<audio>` プレイヤー（ダッシュボード行・詳細画面）
- 認証付き音声配信エンドポイント `GET /api/transcripts/{id}/audio`（Range 対応）
- 音声手動削除エンドポイント `DELETE /api/transcripts/{id}/audio`
- セグメント `start_seconds` / `end_seconds` の DB 保存

#### v1.1 で実装する内容

- `timeupdate` イベントで現在再生時刻に該当するセグメントを判定しハイライト
- 再生中はアクティブカードを自動スクロールしてビューポート内に保つ（ユーザーが手動スクロールしている時は中断する配慮）
- セグメントカードクリック → `audio.currentTime = segment.start_seconds` でシーク
- 編集モードとシーク操作の優先度ルール明確化（編集モード中のカードクリックは編集に割り当てる等）
- 速度変更・スキップ（±5 秒）のキーボードショートカット（任意）

#### 設計検討点（実装着手前に詰める）

## v1.0.2 ストレージ管理機能（2026-05-13 確定スコープ）

Railway Hobby Plan のストレージ上限 5 GB を意識した運用機能。データの安全な廃棄（セキュリティ）と、ストレージ満杯による書き込み失敗の予防（信頼性）の両立が目的。

### スコープ（確定）

#### 1. 自動削除機能

- **対象**: 文字起こし完了から所定日数経過したデータの**音声・テキスト・DB レコードすべてを物理削除** (β スコープ)
  - ソフト削除ではなく物理削除。セキュリティ最優先の方針
  - ユーザー操作の削除（`DELETE /api/transcripts/{id}`）はソフト削除のままで、両者は別パス
- **保管期間**: デフォルト 60 日。環境変数 `DATA_RETENTION_DAYS` で運用中に調整可能
- **削除日時の判定**: `completed_at + DATA_RETENTION_DAYS` を毎回計算（カラム追加なし。計算ロジックは 1 関数に集約しておき、将来 `expires_at` カラム化したくなった時に局所変更で済むよう備える）
- **削除タイミング**: バックグラウンドタスクで 1 日 1 回スキャン（FastAPI lifespan + asyncio loop）
- **削除前のユーザー通知**: 画面のカウントダウン表示のみ（メール通知は将来候補）

#### 2. カウントダウン表示

文字起こし完了から自動削除までの残り日数を表示。**ダッシュボードと詳細画面で表示ポリシーが異なる**:

| 残り日数 | ダッシュボード（履歴行） | 詳細画面 |
|---|---|---|
| 30 日超 | **非表示**（情報過多を防ぐ） | 「📅 あと 45 日で自動削除」（グレー控えめ） |
| 7〜30 日 | 「🟡 あと 28 日で削除」（黄色） | 同左 |
| 1〜7 日 | 「🔴 あと 3 日で削除」（赤・太字） | 同左 |
| 当日 | 「🔴 まもなく削除」（赤） | 同左 |

- **エクスポート促進文言・リンクは付けない**（数値とアイコンのみ）。エクスポート動線は既存メニューからアクセス可能で十分というユーザー判断
- ダッシュボードでは安全域（30 日超）を非表示にして情報過多を防ぐ

#### 3. ストレージ使用量・コスト表示の再設計（UX-1 ハイブリッド）

「**管理者向け指標はユーザー動線を圧迫しない**」方針に基づき、ストレージ使用量と既存の月次コスト表示をホーム画面上部から **ヘッダーに統合**する。

##### 3.1 ヘッダーに常時表示するアイコン状態

ヘッダー（右上のユーザーメニュー隣）に、ストレージとコストの状態アイコンを 2 つ並べる:

| 状態 | 視覚 |
|---|---|
| 通常時（〜70% / 〜80%） | アイコン + 数値（小、グレー控えめ） |
| 注意（70-90% / 80-100%） | 黄色アイコン |
| 警告（90% 超 / 100% 超） | 赤アイコン |

- タップ/クリックで**詳細ポップオーバー**（PC）or **bottom sheet**（スマホ）が開き、バー表示と詳細文言が見える
- **既存の `.monthly-cost-summary` セクション（ホーム画面上部の月次コスト集計バー）は廃止**し、ヘッダー統合に置き換える
- ホーム上部はユーザー動線（アップロード + 履歴）のみに解放される

##### 3.2 警告時の上部バナー

ストレージ警告域に入った場合、ホーム画面上部に**バナー**として明示的に通知:

| 使用率 | バナー文言 | 色 |
|---|---|---|
| 〜70% | 表示しない | — |
| 70〜90% | 「ストレージ使用量: 3.6 GB / 5 GB (72%) — 古い文字起こしを整理しましょう」 | 黄 |
| 90% 以上 | 「容量が満杯に近づいています: 4.6 GB / 5 GB (92%) — 削除してから新規アップロードしてください」 | 赤 |

##### 環境変数

- `STORAGE_LIMIT_BYTES`（default 5 GB ＝ Hobby Plan 上限）
- `STORAGE_WARNING_PERCENT`（default 70）
- `STORAGE_DANGER_PERCENT`（default 90）

##### ストレージ使用量の計算

`/data/audio/` を `os.scandir` で 1 パススキャン（数千ファイルでも数ミリ秒）。ホーム画面・詳細画面のレンダリング時に取得する。

#### 4. アップロード時ガード

##### 4.1 サーバー側の最終チェック

`POST /api/transcripts` で「現在使用量 + 新規ファイルサイズ > 上限の 95%」のときは 413 を返す。

- 環境変数 `STORAGE_HARD_LIMIT_PERCENT`（default 95）
- DB ファイル成長・一時ファイル展開で予想外に膨らんでも対応できる安全マージン
- 同時利用時のレース（A 送信中に B が完了 → 95% 超）は受信開始時の Content-Length + 現在使用量で予測判定し、可能なら受信前に拒否

##### 4.2 クライアント側の予防警告

UX-1 ハイブリッドのヘッダー表示用に取得済みの使用量を流用し、ファイル選択した瞬間にチェック:

- 「現在使用量 + 選択ファイルサイズ > 95%」のとき、**アップロードフォーム内に赤いエラーテキストを表示**
- アップロード開始ボタンを無効化
- 文言: 「ストレージが満杯です (4.9 GB / 5 GB)。**[古いものから整理する]** をクリックして空きを作ってください」
- **「古いものから整理する」リンク**: クリックで履歴一覧へスクロール + ソート（後述）を「古い順」に自動切替

##### 4.3 注意点（実装時）

- クライアント側の予防警告は補助機能で、最終的な安全網はサーバー側の 4.1 チェック
- 5 GB を絶対超えない運用（市川さん希望）のため、クライアント・サーバー両面で守る

#### 5. 履歴一覧のソート機能

UX-3 の「整理リンク」で「古い順に並び替え」を実装するついでに、汎用ソート機能を v1.0.2 に同梱する。

##### スコープ

| ソート軸 | モード |
|---|---|
| 作成日 | 新しい順（現在のデフォルト） / 古い順 |
| 名前 | あいうえお順 / 逆順 |

→ 計 4 モード。

##### UI

- 履歴一覧ヘッダーの右側に**ドロップダウン**「並び順: 新しい順 ▾」
- クリックで 4 モードのメニュー表示

##### 実装方針

- **クライアント側ソート（Alpine.js）**。サーバー API 変更不要
- 並び替えても次の `outerHTML` 差し替え（HTMX の processing 行 polling）でソート順が壊れないよう、ソート状態を Alpine state で保持
- 新規アップロード時の HTMX `afterbegin` 挿入は、ソート「古い順」のとき自然な挙動とする（新着は別扱いで一番上、v1.0.2 ではそのまま）

##### 整理リンクとの連携

UX-3 の「[古いものから整理する]」リンクをクリックすると:

1. 履歴一覧へスクロール
2. ソートを「古い順」に自動切替（Alpine state を変更）
3. ユーザーは一番上に表示された最古ファイルから削除可能

## v1.x スマホ対応（2026-05-13 確定スコープ、リリース粒度は別途決定）

「会議終わりにスマホから直接アップロード」を主目的に、以下の範囲でスマホ対応を行う。UI/UX のビジュアル細部はアートディレクター + ユーザー視点での専用レビューセッションで再検討する。

### スコープ（確定）

- **対応形式の拡張**: 現状の `.mp3 / .mp4` に加え `.m4a / .wav / .mov` を許可（iPhone ボイスメモの m4a 等を直接アップロード可能に）
- **ホーム画面**: スマホ縦画面で快適にアップロード・履歴閲覧できるよう CSS レスポンシブ対応（タッチターゲット 44px 以上、情報密度調整、ハンバーガー/ドロワー化の検討）
  - 2026-05-13 のスマホ実機確認で次の課題が判明（#4 ホーム画面レスポンシブで対応する）:
    - 「ヘルプ」「ログアウト」のテキストが途中で折り返してしまう（flex 子要素の幅不足）
    - ストレージ・コストインジケーターのポップオーバーが画面左端を超えてはみ出る（`right: 0` 配置だが画面外まで飛び出る）
    - ヘッダー全体が情報過多で窮屈
  - 対応方針: スマホ幅ではハンバーガーメニュー化してヘルプ・ユーザー名・ログアウトを畳む。ポップオーバーは UX-1 確定通り bottom sheet 化する
- **詳細画面（閲覧・再生）**: スマホで読み・聞きが快適にできるよう CSS のみ最適化
- **詳細画面（編集 UI）**: スマホでも軽編集（テキスト訂正・話者リネーム）は許可。ただし以下の対応が必要:
  - PC のダブルクリック → 編集モード入りは残す（Notta 互換）
  - スマホではダブルタップでの編集モード入りを無効化（iOS 拡大ジェスチャーと衝突）
  - Shift+Return での分割はスマホで動かない（Shift キーがない）ため、**代案として「ここで分割」ボタンを追加**
- **「ここで分割」ボタン**: 編集中の textarea にフォーカス時のみ表示。カーソル位置で分割（Shift+Return と完全同等の動作）。PC でも併存させて発見性を上げる
- **アップロード進捗の改善**: バー表示 + 完了確認画面（モバイル回線での体感品質改善）
- **誤操作対策**: スマホでは編集モード OFF をデフォルトに、編集モード ON 時のみ編集 UI を露出
- **編集モード時のヒント文** (`.edit-hint` の「ダブルクリックで編集 / Shift + Return で分割 / 自動保存」): スマホでは PC ショートカット 2 つが該当しないので、スマホでは**丸ごと非表示**にする (もしくはスマホ専用文言「タップで編集 / 自動保存」に差し替え。UI/UX 専用レビューで最終決定)

### スコープ外（明示）

- スマホでの c スコープ相当（編集 UI の本格再設計）は不要と判断。スキマ時間の軽編集が主用途
- PWA 化や Web Share Target API 連携は別途（将来候補）

### UI/UX レビューでの再検討対象（後で）

- ヘッダー圧縮（ハンバーガーメニュー化）の要否
- 話者編集ポップアップのモバイル配置（bottom sheet 化など）
- アップロード完了確認画面のビジュアル
- 「ここで分割」ボタンのアイコン・配置・文言
- 履歴一覧のスマホ縦表示時の情報優先度

### 将来候補

- PWA + Web Share Target（iPhone ボイスメモの「共有」シートから直接アップロード）
- スマホでも編集 UI の本格再設計（c スコープ、需要を見てから判断）

### 旧 API のクリーンアップ

- [x] **`PATCH /api/transcripts/{id}/speakers/{speaker_label}` を削除** (ef24882)

### 見送り（2026-05-13 レビュー判断）

- ⏸ **CSRF トークンの導入**
  - 理由: `fetch()` で `Content-Type: application/json` を使うため、クロスサイトフォームから直接送信できない。`DELETE /api/transcripts/{id}` も CORS プリフライト必須。社内 5〜8 人運用では実害リスクが極めて小さい
  - 再検討タイミング: 公開範囲を広げる時、契約・法務要件で求められる時
- ⏸ **`split_segment` の `order_index` UNIQUE 制約強化**
  - 理由: 現状の +1 一括シフト実装は UNIQUE 化すると一時的に違反する SQL になる（PostgreSQL なら DEFERRABLE 必須）。SQLite 単一ライター運用では実害なし
  - 再検討タイミング: PostgreSQL 移行時、複数ワーカー化時
- ⏸ **9 人以上の話者で色が重複する問題**
  - 理由: 社内 5〜8 人想定のため通常運用で発生しない
  - 再検討タイミング: 長尺会議で頻発するようになったら（枠線パターン併用案、または色数 12 拡張）
- ⏸ **`transcript.status` の中間段階の可視化**
  - 理由: ETA 表示（「あと約 X 分」）で実用上は十分代替できている
  - 再検討タイミング: ユーザーから「いま何やってるかわからない」フィードバックが出てきたら
