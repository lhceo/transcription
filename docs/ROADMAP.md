#### 設計確定事項（2026-05-13 設計レビュー）

3 視点 (ユーザー / アートディレクター / 第三者エンジニア) のレビューで詰めた仕様:

##### 1. クリック動作 (モード依存 + 自動再生)

- **View mode** (編集 OFF): セグメントクリック = `audio.currentTime = seg.start_seconds` でシーク。**停止中でも自動再生開始**（「クリック = ここを聴く」が 1 アクションで完結）
- **Edit mode** (編集 ON): セグメントクリック = textarea にフォーカス（編集に専念）。シークは ±3 秒ボタン or 別カードクリックで（編集中もリスニングと往復する想定）

##### 2. ハイライト方式: 線形補間カラオケ

- セグメント単位の `start_seconds` / `end_seconds` を使用し、セグメント内では**時間 → 文字位置を線形補間**で算出
- AssemblyAI が返す word-level タイムスタンプは使わない（既存データに保存していない + 移行コストが高いため、新旧データの差異が出る方を避ける）
- 「ズレが出るのは許容範囲」（市川さん判断）

##### 3. ハイライトの視覚

- **進行済み文字**: 蛍光黄 (`#fef08a`) の半透明背景（カラオケ表現）
- **アクティブセグメント**: 薄い水色背景（カード全体がハイライト）
- 文字色変化のトランジション 100-200ms（じんわり）
- セグメント切替時のフェード 200ms
- 一時停止中: 進行は止まるが、ハイライトは現在位置で残る

##### 4. 自動スクロール

- **賢いスクロール**: アクティブセグメントが**ビューポート外に出た時のみ**追従（ビューポート内なら動かない）
- アニメーション: `scrollIntoView({ behavior: 'smooth', block: 'start' })` で 300-400ms
- **手動スクロール時の中断ルール**: ユーザーの手動スクロール（touchmove / wheel / scrollbar drag）を検知 → auto-scroll 一時停止 → 「**現在の発言に戻る**」ボタン（FAB）が出現 → ユーザーが明示的にタップして再開
- 時間による自動再開はしない（予測可能性優先、Notta 同様）

##### 5. 音声プレイヤーの常時アクセス性

- 音声プレイヤーを **画面上部に sticky 配置**（編集中も操作可能、スクロールしても消えない）
- スマホでは**コンパクト化** (高さ 44-50px)
- プレイヤー内に以下を併設:
  - 再生 / 停止
  - **±3 秒ボタン**（ラベル: `[⏪3]` / `[+3⏩]` アイコン + 数字）
  - **速度変更ドロップダウン** (0.5x / 0.75x / 1x / 1.25x / 1.5x / 1.75x / 2x、LocalStorage 保存)
  - 進行バー / 時刻表示

##### 6. キーボードショートカット (PC のみ)

| キー | 動作 |
|---|---|
| `Space` | 再生 / 停止 |
| `← / →` | ±3 秒戻る / 進む |
| `Shift + Enter` | セグメント分割（既存維持） |

スマホでは全ボタン操作で完結（キーボード操作なし、v1.0.3 と同方針）。

##### 7. 2 つの FAB の位置と視覚階層 (編集中の競合回避)

「ここで分割」と「現在の発言に戻る」が同時表示される可能性があるため、位置と視覚で住み分け:

| FAB | 位置 | スタイル | 出現条件 |
|---|---|---|---|
| 「ここで分割」 | 画面右下 | **プライマリ青、太字、フル不透明** | textarea にフォーカス時 |
| 「現在の発言に戻る」 | 画面下中央 | **セカンダリグレー、半透明、やや小さめ** | autoScrollPaused = true 時 |

両 FAB とも v1.0.3 で実装した visualViewport API を流用してキーボード上に追従。

##### 8. 手動スクロール検知の精度設計 (実装メモ)

誤検知で auto-scroll が頻繁停止しないよう、3 段階チェック:

```javascript
let isAutoScrolling = false;
let lastScrollY = 0;
function handleScroll() {
    if (isAutoScrolling) return;  // 1. 自分起因なら無視
    if (Math.abs(window.scrollY - lastScrollY) > 5) {  // 2. 5px 以上の変化のみ
        autoScrollPaused = true;
    }
    lastScrollY = window.scrollY;
}
```

`touchmove` でも検知（タップでは発火しない `touchmove` を使う）。

##### 9. 音声なし transcript の扱い

- 音声プレイヤー、±3 秒ボタン、速度変更、同期ハイライト、クリックシーク、キーボードショートカットすべて非表示 / 無効化

- 編集機能・話者リネーム・エクスポートは通常通り動作（後方互換）

## v1.0.2 ストレージ管理機能（2026-05-13 確定スコープ）

Railway Hobby Plan のストレージ上限 5 GB を意識した運用機能。データの安全な廃棄（セキュリティ）と、ストレージ満杯による書き込み失敗の予防（信頼性）の両立が目的。

### スコープ（確定）

#### 1. 自動削除機能

- **対象**: 文字起こし完了から所定日数経過したデータの**音声・テキスト・DB レコードすべてを物理削除** (β スコープ)
  - ソフト削除ではなく物理削除。セキュリティ最優先の方針
  - ユーザー操作の削除（`DELETE /api/transcripts/{id}`）はソフト削除のままで、両者は別パス
- **保管期間**: デフォルト 60 日。環境変数 `DATA_RETENTION_DAYS` で運用中に調整可能
- **削除日時の判定**: `completed_at + DATA_RETENTION_DAYS` を毎回計算（カラム追加なし。計算ロジックは 1 関数に集約しておき、将来 `expires_at` カラム化したくなった時に局所変更で済むよう備える）
- **削除タイミング**: バックグラウンドタスクで 1 日 1 回スキャン（FastAPI lifespan + asyncio loop）
- **削除前のユーザー通知**: 画面のカウントダウン表示のみ（メール通知は将来候補）

#### 2. カウントダウン表示

文字起こし完了から自動削除までの残り日数を表示。**ダッシュボードと詳細画面で表示ポリシーが異なる**:

| 残り日数 | ダッシュボード（履歴行） | 詳細画面 |
|---|---|---|
| 30 日超 | **非表示**（情報過多を防ぐ） | 「📅 あと 45 日で自動削除」（グレー控えめ） |
| 7〜30 日 | 「🟡 あと 28 日で削除」（黄色） | 同左 |
| 1〜7 日 | 「🔴 あと 3 日で削除」（赤・太字） | 同左 |
| 当日 | 「🔴 まもなく削除」（赤） | 同左 |

- **エクスポート促進文言・リンクは付けない**（数値とアイコンのみ）。エクスポート動線は既存メニューからアクセス可能で十分というユーザー判断
- ダッシュボードでは安全域（30 日超）を非表示にして情報過多を防ぐ

#### 3. ストレージ使用量・コスト表示の再設計（UX-1 ハイブリッド）

「**管理者向け指標はユーザー動線を圧迫しない**」方針に基づき、ストレージ使用量と既存の月次コスト表示をホーム画面上部から **ヘッダーに統合**する。

##### 3.1 ヘッダーに常時表示するアイコン状態

ヘッダー（右上のユーザーメニュー隣）に、ストレージとコストの状態アイコンを 2 つ並べる:

| 状態 | 視覚 |
|---|---|
| 通常時（〜70% / 〜80%） | アイコン + 数値（小、グレー控えめ） |
| 注意（70-90% / 80-100%） | 黄色アイコン |
| 警告（90% 超 / 100% 超） | 赤アイコン |

- タップ/クリックで**詳細ポップオーバー**（PC）or **bottom sheet**（スマホ）が開き、バー表示と詳細文言が見える
- **既存の `.monthly-cost-summary` セクション（ホーム画面上部の月次コスト集計バー）は廃止**し、ヘッダー統合に置き換える
- ホーム上部はユーザー動線（アップロード + 履歴）のみに解放される

##### 3.2 警告時の上部バナー

ストレージ警告域に入った場合、ホーム画面上部に**バナー**として明示的に通知:

| 使用率 | バナー文言 | 色 |
|---|---|---|
| 〜70% | 表示しない | — |
| 70〜90% | 「ストレージ使用量: 3.6 GB / 5 GB (72%) — 古い文字起こしを整理しましょう」 | 黄 |
| 90% 以上 | 「容量が満杯に近づいています: 4.6 GB / 5 GB (92%) — 削除してから新規アップロードしてください」 | 赤 |

##### 環境変数

- `STORAGE_LIMIT_BYTES`（default 5 GB ＝ Hobby Plan 上限）
- `STORAGE_WARNING_PERCENT`（default 70）
- `STORAGE_DANGER_PERCENT`（default 90）

##### ストレージ使用量の計算

`/data/audio/` を `os.scandir` で 1 パススキャン（数千ファイルでも数ミリ秒）。ホーム画面・詳細画面のレンダリング時に取得する。

#### 4. アップロード時ガード

##### 4.1 サーバー側の最終チェック

`POST /api/transcripts` で「現在使用量 + 新規ファイルサイズ > 上限の 95%」のときは 413 を返す。

- 環境変数 `STORAGE_HARD_LIMIT_PERCENT`（default 95）
- DB ファイル成長・一時ファイル展開で予想外に膨らんでも対応できる安全マージン
- 同時利用時のレース（A 送信中に B が完了 → 95% 超）は受信開始時の Content-Length + 現在使用量で予測判定し、可能なら受信前に拒否

##### 4.2 クライアント側の予防警告

UX-1 ハイブリッドのヘッダー表示用に取得済みの使用量を流用し、ファイル選択した瞬間にチェック:

- 「現在使用量 + 選択ファイルサイズ > 95%」のとき、**アップロードフォーム内に赤いエラーテキストを表示**
- アップロード開始ボタンを無効化
- 文言: 「ストレージが満杯です (4.9 GB / 5 GB)。**[古いものから整理する]** をクリックして空きを作ってください」
- **「古いものから整理する」リンク**: クリックで履歴一覧へスクロール + ソート（後述）を「古い順」に自動切替

##### 4.3 注意点（実装時）

- クライアント側の予防警告は補助機能で、最終的な安全網はサーバー側の 4.1 チェック
- 5 GB を絶対超えない運用（市川さん希望）のため、クライアント・サーバー両面で守る

#### 5. 履歴一覧のソート機能

- ⏸ **CSRF トークンの導入**
  - 理由: `fetch()` で `Content-Type: application/json` を使うため、クロスサイトフォームから直接送信できない。`DELETE /api/transcripts/{id}` も CORS プリフライト必須。社内 5〜8 人運用では実害リスクが極めて小さい
  - 再検討タイミング: 公開範囲を広げる時、契約・法務要件で求められる時
- ⏸ **`split_segment` の `order_index` UNIQUE 制約強化**
  - 理由: 現状の +1 一括シフト実装は UNIQUE 化すると一時的に違反する SQL になる（PostgreSQL なら DEFERRABLE 必須）。SQLite 単一ライター運用では実害なし
  - 再検討タイミング: PostgreSQL 移行時、複数ワーカー化時
- ⏸ **9 人以上の話者で色が重複する問題**
  - 理由: 社内 5〜8 人想定のため通常運用で発生しない
  - 再検討タイミング: 長尺会議で頻発するようになったら（枠線パターン併用案、または色数 12 拡張）
- ⏸ **`transcript.status` の中間段階の可視化**
  - 理由: ETA 表示（「あと約 X 分」）で実用上は十分代替できている
  - 再検討タイミング: ユーザーから「いま何やってるかわからない」フィードバックが出てきたら
