# セキュリティ方針（SECURITY.md）の骨子

このファイルは Web アプリのセキュリティ設計方針を整理したものです。  
**「骨子」** として、最低限の方針を明示し、実装フェーズで詳細を詰めていきます。

最終更新: 2026-05-12

---

## 1. 守るべきもの（資産）

優先度順に：

| 資産 | 重要度 | 漏洩時の影響 |
|---|---|---|
| **お客様の音声データ** | 最高 | 信用失墜・法的責任 |
| **文字起こし結果（テキスト）** | 高 | 機密情報漏洩 |
| **ユーザー認証情報（セッション）** | 高 | なりすまし、不正利用 |
| **AssemblyAI API キー** | 高 | 高額の不正利用 |
| **ユーザー情報（メール・名前）** | 中 | プライバシー侵害 |
| **話者名履歴** | 低〜中 | 関係者の名前が漏れる |

## 2. 脅威モデル

### 想定する攻撃シナリオ

| 脅威 | 想定攻撃者 | 対策 |
|---|---|---|
| **不正アクセス** | 外部の悪意ある第三者 | Google OAuth + ドメイン制限 |
| **API キー流出** | コード公開ミス、サーバー侵入 | 環境変数管理、AssemblyAI 側で上限設定 |
| **音声データ漏洩** | サーバー侵入、内部漏洩 | 処理完了後即削除、HTTPS 通信 |
| **CSRF 攻撃** | 悪意あるサイトへの誘導 | SameSite Cookie + CSRF トークン |
| **SQL インジェクション** | 入力経由の攻撃 | ORM 使用、生 SQL 書かない |
| **XSS（クロスサイトスクリプティング）** | 結果に紛れる悪意ある文字列 | テンプレートエンジンの自動エスケープ |
| **退職者の不正アクセス** | 元社員 | Google Workspace 連携で即時無効化 |
| **総当たり攻撃** | 自動化ツール | レート制限（将来）、Google OAuth に委譲で実質防御 |
| **依存ライブラリの脆弱性** | サプライチェーン攻撃 | Dependabot 通知、定期更新 |

### 想定しない攻撃（スコープ外）

- 国家レベルの高度な攻撃（APT）
- 物理的なサーバーアクセス（Railway 側の責任範囲）
- DDoS の本格攻撃（Railway / CDN レベルでの保護を期待）

## 3. 認証（Authentication）

### 方式

- **Google OAuth 2.0** を唯一の認証手段とする
- パスワード認証は実装しない（管理コスト削減）
- 認証ライブラリ: `authlib`（Python の OAuth 標準ライブラリ）

### Google OAuth フロー詳細

`ARCHITECTURE.md` のシーケンス図参照。重要なポイント：

1. **state パラメータ**: ランダムな文字列をセッションに保存し、コールバック時に検証（CSRF 防止）
2. **PKCE 利用**: モダンな OAuth 2.0 ベストプラクティス
3. **ID トークンの検証**: 署名検証 + `aud`（audience）が自分のクライアント ID か確認
4. **メールアドレスの検証**: `email_verified` フラグを必ずチェック

### ドメイン制限

- ID トークンの `email` フィールドのドメイン部を検証
- 許可リスト（例: `["lionheart.co.jp"]`）を環境変数で設定
- 許可外のドメインは即座にログアウト＋エラー画面
- **複数ドメインの許可は将来対応**（社外協力者などに開放したい場合）

### セッション管理

- **方式**: 署名付き Cookie（DB セッションテーブルなし）
- **Cookie 属性**:
  - `HttpOnly`: JavaScript からアクセス不可（XSS 緩和）
  - `Secure`: HTTPS のみで送信
  - `SameSite=Lax`: 通常のリンクはOK、フォーム POST やフレーム埋め込みは制限
- **有効期限**: 14日（ブラウザを閉じても保持）
- **再認証**: 14日経過 or 明示的なログアウトで再ログインを要求

## 4. 認可（Authorization）

### 原則

- **リソースの所有者のみアクセス可能**
- 他人の `transcripts` を見る・編集することは不可
- 管理者ロール等は v1 では実装しない

### 実装パターン

すべての protected エンドポイントで以下のチェックを行う：

```python
# 擬似コード
def get_transcript(transcript_id: int, current_user: User):
    transcript = db.query(Transcript).filter_by(id=transcript_id).first()
    if not transcript:
        raise NotFoundError()
    if transcript.user_id != current_user.id:
        raise NotFoundError()  # 403 ではなく 404 を返す（存在を漏らさない）
    return transcript
```

### 注意点
- **「存在しない」と「権限がない」を区別しない**（情報漏洩防止）
- どちらの場合も 404 を返す

## 5. CSRF（クロスサイトリクエストフォージェリ）対策

### 方針

3層防御：

1. **SameSite Cookie**（`SameSite=Lax`）
   - 第三者サイトからの POST/PATCH/DELETE には Cookie が送られない
   - **これで多くの CSRF は防げる**

2. **同一オリジン確認**
   - 状態変更リクエストの `Origin` / `Referer` ヘッダを検証

3. **CSRF トークン**（重要操作のみ）
   - ファイル削除、アカウント関連操作などの危険な操作には CSRF トークンを必須化
   - フォームのhidden inputまたはカスタムヘッダで送信
   - サーバー側で検証

### HTMX の場合

HTMX は `hx-headers` でカスタムヘッダを送れるので、CSRF トークンを `X-CSRF-Token` ヘッダに入れる方式が使える。

## 6. ファイルアップロードのセキュリティ

### バリデーション

| 項目 | 制限 | 実装方法 |
|---|---|---|
| **ファイルサイズ** | 2GB 以下 | FastAPI の `UploadFile` でストリーミング検証 |
| **ファイル形式** | mp3 / mp4 のみ受け入れ | 拡張子 + MIME タイプ + マジックナンバー検証 |
| **ファイル名** | 危険な文字を除去 | `secure_filename()` 的な処理 |
| **音声長さ** | 6時間まで | アップロード後 AssemblyAI が返す duration で判定 |

### マジックナンバー検証（重要）

拡張子だけだと偽装可能なので、ファイルの先頭バイトで本物の形式かチェック：

- mp3: `ID3` または `FF FB / FF F3 / FF F2`
- mp4: `66 74 79 70` (ftyp) を 4 バイト目以降に含む

ライブラリ: `python-magic` または `filetype` を使用

### 一時ファイルの扱い

- アップロード先: `/tmp/uploads/{uuid}/{filename}`
- 処理完了後 **必ず削除**（成功時も失敗時も）
- 6時間以上残っている孤立ファイルは定期的にクリーンアップ（cron 的な仕組み）

## 7. API キーとシークレット管理

### 保管場所

| 情報 | 保管先 |
|---|---|
| AssemblyAI API キー | Railway 環境変数 |
| Google OAuth クライアントシークレット | Railway 環境変数 |
| セッション署名キー | Railway 環境変数（強力なランダム文字列） |
| **Git にコミットするもの** | **絶対なし** |

### `.env` ファイル運用

- ローカル開発用に `.env` を使う（`.gitignore` に追加）
- `.env.example` を用意してテンプレート提供（実値なし）
- ローカル開発用のキーと本番用のキーは分ける

### 流出時の対応

1. **AssemblyAI**: ダッシュボードで該当キーを即座に Revoke、新規発行、環境変数更新、再デプロイ
2. **Google OAuth**: Google Cloud Console でクライアントシークレットを再生成
3. **セッションキー**: 新しい値に変更（既存セッションは全て無効化される）

## 8. データ保護

### 通信路

- **HTTPS 必須**（Railway が自動で SSL 提供）
- 内部通信（FastAPI ↔ AssemblyAI）も HTTPS
- HTTP 接続は HTTPS にリダイレクト

### 保存時の暗号化

- **DB（SQLite）**: Railway の永続ボリュームは暗号化されている（Railway 側の責任）
- **追加でアプリ側で暗号化はしない**（v1）
- 将来必要になったら、特に機密度の高いカラムだけアプリ層で暗号化を追加

### 音声データの取り扱い

| 段階 | 場所 | 暗号化 | 保持期間 |
|---|---|---|---|
| アップロード中 | ブラウザ → サーバー | HTTPS | 通信時のみ |
| 一時保存 | サーバー /tmp | OS レベル（Railway） | 数分〜数時間 |
| AssemblyAI 転送 | サーバー → AssemblyAI | HTTPS | 通信時のみ |
| AssemblyAI 処理中 | AssemblyAI のサーバー | AssemblyAI 側で暗号化 | 数分〜数十分 |
| 処理完了後 | **どこにも残さない** | - | 即削除 |

### 文字起こし結果（テキスト）

- DB に永続保存される
- 暗号化は v1 ではアプリ層で追加しない
- ユーザーが「削除」を実行すれば soft delete → 30日後 hard delete

## 9. 入力検証

### 原則

- **全ての入力は信用しない**（クライアント送信値はもちろん、外部 API の応答も）
- **サーバー側で必ず検証**（クライアント側はUX向上のためのみ）

### SQL インジェクション対策

- **SQLAlchemy ORM を使用**
- 生 SQL を書く場合は **必ずパラメータバインディング**
- 文字列連結で SQL を組み立てない

### XSS 対策

- テンプレートエンジン（Jinja2）の自動エスケープを有効化
- ユーザー入力を `|safe` フィルタで信頼しない
- HTMX で innerHTML を扱う場合は特に注意

### ヘッダのセキュリティ

実装時に以下の HTTP ヘッダを設定：

| ヘッダ | 値 | 目的 |
|---|---|---|
| `Content-Security-Policy` | strict 設定 | XSS 緩和 |
| `X-Content-Type-Options` | `nosniff` | MIME スニッフィング防止 |
| `X-Frame-Options` | `DENY` | クリックジャッキング防止 |
| `Referrer-Policy` | `strict-origin-when-cross-origin` | リファラ情報の漏洩防止 |
| `Strict-Transport-Security` | 1年 | HTTPS 強制（HSTS） |

ライブラリ: `secure` または FastAPI ミドルウェアで一括設定

## 10. レート制限

### v1 では実装しない（理由）

- 5〜8人の社内利用で攻撃面が限定的
- AssemblyAI 側の月額上限（C-1 で設定）が実質的な防護壁
- 認証が Google OAuth なので、無認証で API を叩けない

### 実装する場合の指針（将来）

- 上限: 1ユーザーあたり 1時間に 10ジョブまで
- 実装: `slowapi` ライブラリ
- レート制限超過時: `429 Too Many Requests` を返す

## 11. ログとモニタリング

### 記録するもの

- ログイン成功・失敗
- 文字起こしジョブ作成・完了・失敗
- 削除操作
- エラー（スタックトレース付き）
- 不正なアクセス試行（権限違反、ドメイン違反）

### 記録しないもの（重要）

- パスワード（そもそも保管していない）
- セッショントークン本体
- API キー本体
- 音声データの内容
- 文字起こし結果のテキスト本体（ID のみ記録）
- ユーザーのメールアドレス（必要時のみ匿名化して記録）

### 監視ツール

| ツール | 用途 | 無料枠 |
|---|---|---|
| **Railway ログ** | リアルタイムログ確認 | 含まれる |
| **Sentry** | エラー追跡、スタックトレース | 5,000イベント/月 |
| **UptimeRobot** | 死活監視（5分間隔） | 50モニター |

→ v1 は **Railway ログ + Sentry の無料枠** でスタート

## 12. インシデント対応

### 想定インシデントと対応手順

#### A. AssemblyAI API キー流出疑い
1. AssemblyAI ダッシュボードでキーを Revoke
2. 異常利用がないか確認
3. 新規キー発行
4. Railway 環境変数を更新
5. 再デプロイ
6. 流出元の特定と修正

#### B. ユーザーアカウント不正利用
1. Google Workspace 管理画面で該当アカウントを停止
2. アプリ側のセッションを強制ログアウト（セッションキーを再生成）
3. アクセスログを確認
4. 影響を受けた transcripts を特定

#### C. データ漏洩疑い
1. アクセスログから漏洩範囲を特定
2. 影響を受けたユーザーへの連絡（必要なら）
3. 漏洩経路の遮断と再発防止
4. 必要に応じて関係者・法的対応

### 連絡フロー

- 開発者（あなた）→ 社内責任者 → 必要なら顧客への連絡
- 連絡先と判断フローは別途定める（運用 SOP として）

## 13. 退職者・人事変更への対応

### Google Workspace 側で完結

- 退職者の Google アカウントを Google Workspace 管理画面で **suspend / delete**
- 次回その人がアクセスを試みると、OAuth が失敗してログイン不可
- アプリ側で何もする必要はない

### アプリ側で追加対応する場合（将来）

- 退職者のデータをどう扱うか方針を定める
  - 結果データを保持？削除？引き継ぎ？
- 引き継ぎ機能（特定の transcripts を別ユーザーに移譲）

## 14. 開発時のセキュリティ習慣

### コードレビュー観点

- [ ] 入力値検証は server-side で行っているか
- [ ] SQL は ORM 経由か、パラメータバインディング済みか
- [ ] エラーメッセージで内部情報を漏らしていないか
- [ ] シークレットがコードに埋め込まれていないか
- [ ] 認証・認可チェックが漏れていないか
- [ ] CSRF 対策がされているか
- [ ] ログに機密情報が出ていないか

### 依存ライブラリ管理

- `requirements.txt` または `pyproject.toml` でバージョンをロック
- Dependabot を GitHub 側で有効化（無料）
- 月1回、脆弱性スキャンを実行

## 15. v1 で実装するもの・しないもの

### v1 で確実に実装

- ✅ Google OAuth + ドメイン制限
- ✅ HTTPS 通信
- ✅ SameSite Cookie
- ✅ ORM で SQL インジェクション対策
- ✅ テンプレートエンジンの自動エスケープ
- ✅ ファイルアップロードの形式・サイズ検証
- ✅ AssemblyAI API キーの環境変数管理
- ✅ アプリ側での音声ファイル即削除
- ✅ AssemblyAI への削除依頼
- ✅ 結果データの所有権チェック
- ✅ 統一エラーフォーマット
- ✅ Sentry でのエラー監視

### v1 では実装しない（将来課題）

- ⏳ レート制限
- ⏳ CSRF トークン（SameSite Cookie で多くは防げる）
- ⏳ DB の特定カラム暗号化
- ⏳ 監査ログの専用テーブル
- ⏳ 多要素認証（Google OAuth に任せる）
- ⏳ アカウントロックアウト機能
- ⏳ 異常検知（不自然なアクセスパターンの検知）
- ⏳ 共有リンク機能のセキュリティ（共有自体を実装しない）

### 実装時に判断するもの

- 🤔 マジックナンバーによるファイル形式検証（やった方がいいが少し手間）
- 🤔 セキュリティヘッダの厳密な CSP 設定（HTMX 使用との兼ね合いで調整必要）
- 🤔 アップロード後の一時ファイル自動クリーンアップ（cron 的な仕組みが必要）
